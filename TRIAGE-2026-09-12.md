## 1. Run-and-advance leaves point at the start of the output block

**Status: confirmed. Notebook only — script and Org are not affected.**

### What happens

`jsonyter-notebook-run-cell-and-advance` (`jsonyter.el:3329`) advances
correctly, and then the arriving output drags point backwards.

Reproduced on the fixture notebook in `test/jsonyter-tests.el`, driving
the exact sequence `jsonyter-notebook-run-cell` performs:

```
after advance: point=7  cell1-start=7          ; correct
after output:  point=7  cell0-src-end=7  cell0-end=190  cell1-start=190
cell at point is cell 0 (the one just run!)
text after point: "output ───────────────────────"
```

Point does not move — the *buffer* moves out from under it. It ends up
at the first character of the just-run cell's output frame, with the
whole output between it and the next cell. Exactly as reported.

Both downstream symptoms confirmed:

```
REPEAT: cell-at-point is cell0? t
REPEAT: source jsonyter would re-send = "x = 1"     ; the SAME cell, silently, forever
REPEAT: typing here signals = "Text is read-only"
```

So pressing `S-RET` again re-executes the previous cell rather than
erroring — arguably worse than a failure, since nothing tells the user.
Typing gives `Text is read-only`.

### Root cause

`jsonyter--nb-show-output-as-text` (`jsonyter.el:2763`), the notebook
path that writes output as real buffer text.

In a rendered notebook, cells are laid down back to back: a cell's
overlay spans source *and* output, so `(overlay-end cell)` is exactly
`(overlay-start next-cell)`. On every output refresh the function does

```elisp
(save-excursion
  (delete-region src-end out-end)
  (goto-char src-end)
  ... (insert body) ...)
```

`save-excursion` saves point as a marker with insertion type `nil`,
sitting at `out-end`. `delete-region` collapses that marker to
`src-end`; the subsequent `insert` at `src-end` leaves an
insertion-type-`nil` marker *before* the inserted text. Point is
restored to the front of the new output.

The function already knows about this hazard — it explicitly fixes up
the adjacent cell overlays that suffer the identical collapse:

```elisp
(dolist (o adjacent) (move-overlay o (point) (overlay-end o)))
```

Point simply was not given the same treatment.

This only bites when the cell produces output (empty body ⇒ nothing
inserted ⇒ point is fine), and it fires on *every* refresh, so with
`jsonyter-stream-output` on it re-fires per chunk.

### Why script and Org are immune

Both are `jsonyter--overlay-string-cell-p` cells: their output is an
overlay `after-string` (`jsonyter--nb-show-output-as-string`,
`jsonyter.el:2744`), so no buffer text changes and no marker moves.
Verified for script mode:

```
SCRIPT: point before=21 after=21 (stable=t)
SCRIPT: line at point = "print(2)"
SCRIPT: output overlay end=16, point=21, point-after-output=t
```

`jsonyter-notebook-run-all` is also immune — it re-issues
`goto-char (overlay-start cell)` before each cell.

### Suggested fix

In `jsonyter--nb-show-output-as-text`, carry point across the rewrite
the way the adjacent overlays are carried. Either:

- record `(>= (point) out-end)` before the rewrite and `goto-char
  new-end` after it when that held; or
- replace the `save-excursion` with an explicit `(copy-marker out-end t)`
  (insertion type `t`, so it rides to the end of the inserted text) and
  `goto-char` it afterwards.

Prefer whichever reads better next to the existing `adjacent` fix-up,
and note in the comment that point and the adjacent overlays have the
same failure mode. Do **not** "fix" this in
`jsonyter-notebook-next-cell` (`jsonyter.el:3691`) — that function is
correct; the corruption happens afterwards, asynchronously, and would
still hit a user who advanced by hand.

Check the other `jsonyter--nb-refresh-output` callers still behave:
`jsonyter-notebook-clear-cell-output`, `jsonyter-notebook-clear-all-output`,
and the staleness path. Point ahead of the output region should stay put
in all of them; point *inside* the deleted region has nowhere valid to
go and landing at the new end is fine.

### Tests to add (explicitly requested)

There is currently **no test anywhere** — neither `test/jsonyter-tests.el`
nor `harness/profile/scenarios/` — asserting cursor position after any
`jsonyter-*-run-cell-and-advance`. The only adjacent assertion is
`harness/profile/scenarios/script.el:78`, which checks `C-c C-n` moves
forward. That gap is why this shipped.

Add to `test/jsonyter-tests.el`, using the existing
`jsonyter-tests--with-notebook` / `jsonyter-tests--cell` /
`jsonyter-tests--stream` helpers (no kernel needed — feed output in
kernel shape, as the file's other tests do):

1. **Notebook, the regression.** Go to cell 0; `jsonyter--nb-set-output`
   to `""` (what run-cell does pre-send); `jsonyter-notebook-next-cell`;
   then `jsonyter--nb-append-output` a multi-line stream. Assert
   `(= (point) (overlay-start (jsonyter-tests--cell 1)))` and
   `(eq (jsonyter--nb-cell-at) (jsonyter-tests--cell 1))`.
   Both fail before the fix.
2. **Notebook, streaming.** Same, with several `append-output` calls, so

3. **Notebook, idempotence.** After the above, assert
   `(jsonyter--nb-cell-source (jsonyter--nb-cell-at))` is cell 1's

4. **Notebook, last cell.** Advancing off the final cell must not error

5. **Script and Org, guard rails.** Assert point is unchanged when

   eventual fix does not regress the overlay-string surfaces.

## 2. Kernel id in the mode line

**Status: valid, small, nothing blocking it.**

`jsonyter--session-status-tag` (`jsonyter.el:1129`) renders state only —
`:idle`, `:run`, `:run[ext]`, `:dead`, `:restarting`, `:offline`,
`:starting`, `:no-kernel`, and transfer progress. No id anywhere.

Everything needed already exists:

- `jsonyter--short-id` (`jsonyter.el:1920`) — first 8 chars, already used
  in the REPL banner, already handles a nil/short id.
- `jsonyter-current-kernel-id` (`jsonyter.el:517`) — public accessor.
- `jsonyter--mode-line-string` (`jsonyter.el:1152`) already resolves the
  Org session **at point**, so this automatically satisfies the Org half
  of report #5 ("put it in the bottom bar") with no extra work.

### Notes for the implementer

- Put it in `jsonyter--session-status-tag`, not
  `jsonyter--mode-line-string`, so all four surfaces get it from one
  place.
- Suggested shape `:idle[3f8a9c21]` or `:3f8a9c21/idle` — pick one and
  apply it consistently. Keep it short; this is `mode-line-process` and
  competes for space.
- Make it a defcustom (e.g. `jsonyter-mode-line-show-kernel-id`,
  default `t`). Users on narrow frames will want it off.
- Leave the multi-session summary branch (`:2 kernels!`) alone — ids
  there would be unreadable.
- Show nothing rather than `?` when there is no kernel; `:no-kernel`
  already says it.
- Tests: `jsonyter--session-status-tag` is a pure function of a session
  struct, so assert its output directly for a bound session, an unbound
  one, and with the defcustom off.

## 3. `jsonyter-kernel-reset`

**Status: already implemented, under a different name. Do not add a new command — fix the naming and the docs.**

`jsonyter-restart` (`jsonyter.el:1775`) is exactly the request:

- docstring: *"Restart SESSION's kernel (default the session in play), **keeping its id**"*
- calls the bridge's `restart_kernel` with `:kernel_id id` and keeps
  using that same `id` afterwards — the id is preserved by construction
  (this is Jupyter's `POST /api/kernels/{id}/restart` semantics)
- prompts *"Restart the kernel (all state will be lost)?"* — the kernel
  process is replaced, so all state is cleared
- also drops the stale websocket, renews the event subscription, clears
  the busy flag, and blanks notebook execution counts via
  `jsonyter--after-kernel-reset`
- bound to `C-c C-r` on every surface, plus `jsonyter-org-restart`
  (`jsonyter.el:5325`) for the session at point

### The actual problem

The command *named* `jsonyter-reset` (`jsonyter.el:1818`) does something
completely different: it clears the **client's** busy flag to unstick a
REPL, and deliberately **leaves the kernel running** — its own docstring
says *"[reset — kernel left running]"*. It is bound to `C-c C-k`.

So a user looking for "reset the kernel" finds `jsonyter-reset`, gets a
command that does not touch the kernel, and concludes the feature is
missing. That is a genuine discoverability bug and matches this report
precisely.

### Suggested change

1. **Add `jsonyter-kernel-restart` as an alias for `jsonyter-restart`.**
   Confirmed as wanted — implement this one. Put it next to
   `jsonyter-restart` (`jsonyter.el:1775`):

   ```elisp
   ;;;###autoload
   (defalias 'jsonyter-kernel-restart #'jsonyter-restart
     "Restart this session's kernel, keeping its id and discarding its state.
   An alias for `jsonyter-restart', named to sit with the other
   `jsonyter-kernel-*' commands (`jsonyter-kernel-connect',
   `jsonyter-kernel-reconnect', `jsonyter-kernel-history') where a user
   looking for kernel operations will find it by completion.")
   ```

   An alias, **not** a rename — `jsonyter-restart` appears in the README,
   the commentary key table (`jsonyter.el:70`) and every mode's keymap,
   and `jsonyter-org-restart` delegates to it. Both names must keep
   working. Note `defalias` gives the alias its own docstring but the
   target's `interactive` spec, which is what we want here (`C-c C-r`
   keeps calling `jsonyter-restart`; the alias exists for `M-x`
   discoverability).

   Add it to the README's REPL/notebook/script key tables as the
   long-form name for `C-c C-r`, and mention it in the `jsonyter-reset`
   cross-reference below — a user who lands on `jsonyter-reset` should be
   pointed at `jsonyter-kernel-restart`, since that is the name they were
   most likely searching for in the first place.

2. Rename the misleading one to `jsonyter-unstick` (or
   `jsonyter-repl-unstick`), keeping `jsonyter-reset` as an obsolete
   alias via `define-obsolete-function-alias`.
3. Cross-reference them in both docstrings: `jsonyter-reset` should say
   "to restart the kernel itself and discard its state, use
   `jsonyter-restart'"; `jsonyter-restart` should say "to merely unstick
   a REPL without touching the kernel, see `jsonyter-reset'".
4. README: the REPL key table lists both `C-c C-r` and `C-c C-k` without
   making the distinction obvious. Spell out that one replaces the kernel
   process (same id, no state) and the other touches only Emacs.

If after this the user still wants a distinct `jsonyter-kernel-reset`,
the only behaviour not already covered would be restart **plus** clearing
displayed output (`jsonyter-clear`) in one gesture. Worth asking before
building it.

## 4. Notebook export — `jsonyter-notebook-export-*`

**Status: the bridge now ships it. This is the largest piece of work in
this report and the highest-value one. Nothing is missing server-side;
the entire job is on the Emacs side.**

Two independent halves:

- **§4.1–4.9 — document export** (HTML, PDF, LaTeX, …) through the
  bridge's new nbconvert verbs. Needs a server.
- **§4.10 — script export** (`.py`/`.R`/`.jl`/`.sas` with `# %%`
  dividers). nbconvert cannot do this; it is a local text
  transformation, and it works with no server, kernel or bridge at all.

They share the naming scheme and nothing else. §4.10 can be built first,
alone, and is the smaller job.

> **Correction to the earlier draft of this report.** It said no export
> support existed anywhere and that bridge work was needed first. The
> first half was right about `jsonyter.el`; the second is now obsolete.
> The `jsonyter` Python package **2.0.0** (`EGuthrieWasTaken/jsonyter`,
> `703945c`) ships `jsonyter/export.py` and exposes it over the
> stdio protocol. `jsonyter.el` is the only thing that has not caught up.

Everything below was read from the bridge at `703945c`
(`jsonyter/export.py`, `jsonyter/cli.py`, `README.md` §"Exporting
notebooks"). File references in this section are to the **bridge** repo
unless prefixed `jsonyter.el:`.

---

### 4.1 What the bridge gives you

Two new protocol verbs, both dispatched on the **REST pool**, never a
kernel worker (`cli.py:113-115`), so a five-minute PDF render cannot
queue behind a running `execute` and vice versa. This matters: export is
safe to fire while a cell is running, and the existing
`jsonyter--busy-p` guard should **not** be applied to it.

#### `list_export_formats` — no params

A capability probe. **Never errors** for an unavailable endpoint
(`export.py:110`), so it is always safe to call:

```json
{"available": true,
 "formats": {"html": {"output_mimetype": "text/html"},
             "markdown": {"output_mimetype": "text/markdown"},
             "pdf": {"output_mimetype": "application/pdf"}},
 "reason": null}
```

```json
{"available": false, "formats": {},
 "reason": "this server does not serve the nbconvert endpoints"}
```

`reason` is populated for 404 (endpoints not served), 3xx (auth failed —
"the server redirected to its login page; check the token") and 500.
Only a genuinely unexpected status raises.

**The format list is the server's, not a constant.** Third-party
exporters registered by entry point appear here. Do not hardcode a
format list in `jsonyter.el`; read it from this call. The `formats` keys
are the format strings to pass to `export_notebook`.

#### `export_notebook` — the real work

Params (`cli.py:114-115`): `format`, `server_path`, `cells`, `notebook`,
`name`, `to_path`, `include_outputs`, `sanitize_html`, `timeout`.

`format` is required. **Exactly one** of `server_path` / `cells` /
`notebook` is required — passing zero or two is an immediate error
(`export.py:388`).

| Source | Endpoint | Use it for |
| --- | --- | --- |
| `server_path` | `GET /nbconvert/{fmt}/{path}` | A notebook already saved **in the server's contents namespace** |
| `cells` | `POST /nbconvert/{fmt}` | An in-memory notebook built from the same cell-spec vocabulary `write_notebook` takes |
| `notebook` | `POST /nbconvert/{fmt}` | An existing nbformat dict |

---

### 4.2 The decision that shapes the whole feature: POST, not GET

**`jsonyter.el`'s notebook buffers are local files, so `server_path` is
the wrong mode for them.** This is the single most important thing for
the implementer to get right, and it is easy to get wrong because GET
looks simpler.

`read_notebook` / `write_notebook` are documented in the bridge as
*"local `.ipynb` files; these need no server and no kernel, so the
bridge is usable offline"* (`cli.py:52-56`), and `jsonyter--nb-do-save`
(`jsonyter.el:3078`) duly passes `(expand-file-name buffer-file-name)` —
a **local** path. `server_path`, by contrast, is a path in the Jupyter
server's Contents API namespace. For the ordinary case — a user opens
`~/work/analysis.ipynb` with `jsonyter-notebook-open` against a remote
server — **there is no such server path at all**, and a GET export would
fail with "notebook not found on the server" or, worse, silently export
a different file that happens to share the name.

So:

- **Notebook buffers ⇒ POST with `cells`.** Always. It also exports
  *what the user is looking at*, including unsaved edits and outputs
  from the current session, which is what "export this notebook" means
  to them.
- **`server_path` ⇒ only from `jsonyter-remote-dired`** (`jsonyter.el:4533`),
  which genuinely browses the server's contents namespace and has real
  server paths in hand. That is a natural, cheap addition (§4.7) but it
  is a *different* command from exporting the buffer.

### 4.3 The outputs trap — read this before writing any code

POST mode renders only the outputs present in the notebook you hand it.
`export_notebook`'s `include_outputs` defaults to **`True`** in POST
mode — deliberately opposite to `write_notebook`, because "an export
with no results in it is nearly useless" (bridge README). Good. But:

**`jsonyter--nb-collect-cells` (`jsonyter.el:3057`) cannot currently
supply the outputs.** It emits `:outputs` only for cells with
`jsonyter-outputs-touched` — cells run or cleared *this session*:

```elisp
(and include-outputs
     (overlay-get cell 'jsonyter-outputs-touched)
     (list :outputs (vconcat (mapcar #'jsonyter--nb-output-to-spec ...))
           :execution_count ...))
```

That is exactly right for `write_notebook`, where omitting the key means
"leave the stored output on disk alone". It is exactly wrong for export,
where omitting the key means "this cell has no output" — so **every cell
the user has not re-run this session would export blank.** Open a
notebook full of saved results, export it, get an empty document. This
will be the first bug report if it is missed.

It is worse than it looks: the raw outputs for untouched cells **do not
exist in Emacs at all**. `jsonyter--nb-make-cell` (`jsonyter.el:2820`)
receives `(plist-get cell :outputs)` from the file, renders it to a
display string, and discards the structured form:

```elisp
(let ((rendered (mapconcat ... (plist-get cell :outputs) "")))
  (overlay-put ov 'jsonyter-output-string rendered)   ; string only
  (jsonyter--nb-refresh-output ov))
```

`jsonyter-raw-outputs` is only ever set by `jsonyter--nb-set-output`
with TOUCHED (`jsonyter.el:3195`).

#### Required fix

In `jsonyter--nb-make-cell`, stash the file's outputs on the overlay
under a **new, separate** property:

```elisp
(overlay-put ov 'jsonyter-file-outputs (plist-get cell :outputs))
```

Then in `jsonyter--nb-collect-cells`, for a cell that is *not* touched,
fall back to that property.

**Do not reuse `jsonyter-raw-outputs` for this** — the two hold
different shapes and mixing them will corrupt the payload:

| Property | Shape | Key |
| --- | --- | --- |
| `jsonyter-raw-outputs` | kernel protocol | `:type` |
| `jsonyter-file-outputs` (new) | nbformat, as read from disk | `:output_type` |

`jsonyter--nb-output-to-spec` (`jsonyter.el:3227`) converts kernel shape
→ nbformat and **must not** be applied to the file outputs, which are
already nbformat. `jsonyter--nb-adapt-output` (`jsonyter.el:2585`)
converts the other way, for rendering only. Getting this backwards
produces cells the server rejects or silently renders empty.

Suggested shape, keeping `write_notebook` untouched:

```elisp
(defun jsonyter--nb-collect-cells (&optional include-outputs all-outputs)
  ;; ALL-OUTPUTS (export): an untouched cell contributes the outputs it
  ;; was read from the file with, so an export of a notebook nothing has
  ;; been re-run in still carries its stored results.  `write_notebook'
  ;; must never pass this: there, omitting `:outputs' is what tells the
  ;; bridge to leave the stored output on disk exactly as it was.
  ...)
```

Call it as `(jsonyter--nb-collect-cells t t)` from export only.

Two smaller consequences:

- **`:id`.** `jsonyter--nb-collect-cells` emits `:id` as `:null` for a
  new cell. `write_notebook` assigns ids; the POST export path just
  hands the notebook to nbformat. Verify a `null` id survives
  `_validate_specs`/`_merge_cells` (`export.py:407-413` reuses
  `notebook._merge_cells`) — if not, omit the key for new cells on the
  export path rather than sending `:null`.
- **Markdown and raw cells** carry no outputs and need no special
  handling; they already round-trip through the same collector.

### 4.4 Result shapes

Two shapes, selected by whether `to_path` was passed.

**Inline** (no `to_path`):

```json
{"format": "html", "mimetype": "text/html", "extension": ".html",
 "encoding": "text", "content": "<!DOCTYPE html>...",
 "bundle": false, "resources": []}
```

**Written to disk** (`to_path` given):

```json
{"format": "markdown", "mimetype": "text/markdown", "extension": ".md",
 "path": "/tmp/out/analysis.md", "bytes": 51, "sha256": "...",
 "bundle": true,
 "resources": [{"name": "output_0_0.png", "path": "/tmp/out/output_0_0.png",
                "bytes": 74, "sha256": "..."}]}
```

Note the two shapes are **disjoint**: inline has `content`/`encoding`
per item, on-disk has `path`/`bytes`/`sha256`. Branch on which keys are
present, not on what you think you asked for.

Four properties of the result worth designing around:

1. **`encoding` is `"text"` or `"base64"`.** Text when the bytes decode
   as UTF-8; base64 otherwise. Binary formats (`pdf`, `webpdf`, `qtpdf`,
   `qtpng` — `export.py:36`) are **always** base64 regardless of what
   the server advertises, because webpdf/qtpdf/qtpng inherit the HTML
   exporter's `text/html` mimetype while emitting PDF/PNG bytes. **Never
   branch on `mimetype` to decide how to decode — branch on
   `encoding`.** The bridge has already done that thinking.
2. **A zip is never returned.** Markdown-with-images and friends come
   back from the server as a zip; the bridge always unpacks it
   (`export.py:_unpack_bundle`). `bundle: true` tells you it happened.
   Member names are sanitized to basenames, so a crafted zip cannot
   escape the target directory.
3. **`resources` are keyed by the basename the primary document already
   references.** Write them next to the document and it works as-is.
   With `to_path` the bridge does this for you.
4. **`extension`** is the server-appropriate suffix (`.html`, `.pdf`,
   `.slides.html`, …) — use it to build default filenames rather than
   guessing from the format name.

### 4.5 `to_path` is the right default for binary formats

`to_path` writes on the machine running the **bridge**, which is a
subprocess of Emacs — i.e. the user's local disk. The write is atomic
(temp file in the destination directory + `os.replace`,
`export.py:_atomic_write_bytes`), so an interrupted export cannot
truncate an existing file. If `to_path` names an existing directory or
ends in a separator, the filename is derived from `name`/`server_path`.

Strongly prefer `to_path` over inline for anything binary or large:

- a multi-megabyte PDF as base64 crosses the stdio pipe as one enormous
  JSON line and is then decoded in Emacs — slow, and it makes the line
  reader's buffer spike;
- writing it yourself means `base64-decode-string` plus
  `(coding-system-for-write 'binary)`, and getting either wrong corrupts
  the file silently. `jsonyter--org-write-image` (`jsonyter.el:5410`) is
  the existing example of doing this correctly if you do need it inline;
- bundles with resources need multiple files written next to each other
  with exactly the right basenames — `to_path` already does it.

Recommended rule: **always pass `to_path`** for the file-producing
commands. Reserve inline for a possible "preview this export in a
buffer" command, and only for `encoding: "text"` results.

### 4.6 Errors

A failed export comes back as a normal bridge error line, so the
existing `jsonyter--error-message` path (`jsonyter.el:804`) already
handles it — but `ExportError.to_json` (`export.py:74`) carries three
extra keys worth surfacing, since they turn a dead end into an
actionable message:

| Key | Meaning |
| --- | --- |
| `format` | the format that failed |
| `hint` | actionable toolchain fix, when known (`export.py:48`) |
| `available_formats` | populated **only** for "unknown export format" |

The bridge already does the hard part: it recovers the server's real
message out of nbconvert's HTML error page (`<pre class="traceback">`,
falling back to `<h1>`) so you never see markup, and it distinguishes an
unknown format from a genuine crash by re-probing `/api/nbconvert` on an
ambiguous 500 (`export.py:_handle_ambiguous_500`).

`hint` is the high-value one. `pdf` failing with a bare "Pandoc wasn't
found" is the single most likely first-run failure, and the hint says
exactly what to install **on the Jupyter server** — a distinction users
reliably get wrong, because nbconvert runs server-side, not in
`jsonyter.el` and not in the bridge. Extend `jsonyter--error-message`
(or the export commands' own handler) to append `hint` on its own line,
and to list `available_formats` when present. The existing function
already has precedent for exactly this: it appends a pointed hint for
401/403 and for transfer conflicts.

Toolchain reality, from the bridge README §"Server-side toolchain for
PDF exports" — worth a README note in `jsonyter.el` so users do not file
bugs against the wrong repo:

- `pdf` / `latex` need pandoc + a LaTeX engine (xelatex) on the server;
- `webpdf` needs playwright + chromium on the server, and in a container
  running as root also `c.WebPDFExporter.disable_sandbox = True`;
- a webpdf browser launch failure of *any* kind is reported by nbconvert
  as the same misleading "no suitable chromium executable found".

So: **`html` and `markdown` work essentially everywhere; `pdf` and
`webpdf` frequently do not.** Design the UI so a missing exporter is an
ordinary, well-explained outcome rather than a broken feature —
`list_export_formats` tells you up front, before the user waits two
minutes for a failure.

### 4.7 Proposed Emacs surface

The user's proposed naming is right and matches house style
(`jsonyter-notebook-save-with-outputs`, `jsonyter-notebook-clear-all-output`).

**Core command**

```elisp
(defun jsonyter-notebook-export (format &optional to-path) ...)
```

Interactively: `completing-read` over the keys of
`list_export_formats`'s `formats` — **never a hardcoded list**, so
third-party exporters show up for free — then `read-file-name` defaulting
to the buffer's own name with the result's `extension` substituted.
Cache the format list per bridge process; it cannot change under a
running server, and the probe is one round trip.

**Thin wrappers**, autoloaded, for the formats worth a name of their own:

```elisp
jsonyter-notebook-export-html      jsonyter-notebook-export-markdown
jsonyter-notebook-export-pdf       jsonyter-notebook-export-latex
jsonyter-notebook-export-webpdf    jsonyter-notebook-export-slides
```

Each is a two-line call into the core. Have them check the probe first
and fail with the *server's* reason ("this server does not serve the
nbconvert endpoints", or the missing-exporter list) rather than firing a
request that will take 120 s to fail.

**Also**

- `jsonyter-notebook-export-formats` — show what this server offers.
  Trivial, and the first thing anyone debugging will want.
- `jsonyter-remote-dired-export` in `jsonyter-remote-dired`
  (`jsonyter.el:4533`): export the notebook at point via **`server_path`**
  (the one place a real server path exists), writing the result locally
  with `to_path`. Natural fit with the existing download command; give
  it a key in `jsonyter-remote-dired-mode-map`.
- Keybinding: `C-c C-x` or a `C-c C-e` prefix in
  `jsonyter-notebook-mode-map`. **`C-c C-e` is already taken** —
  `jsonyter-notebook-run-cell` in the notebook map (`jsonyter.el:3717`)
  and `jsonyter-script-run-cell` in the script map (`jsonyter.el:4971`) —
  so pick something else; check for collisions before binding, and do
  not bind anything Org already owns if this is later extended to Org
  buffers.
- **Script export is a separate command with a separate implementation —
  see §4.10.** `jsonyter-notebook-export-script` shares this naming
  scheme but none of this code path: no bridge call, no format probe, no
  async. Do not try to fold it into the `format` completion list here;
  nbconvert's own `script` format is a different (and wrong) thing.
- Out of scope for a first pass: *document* export from Org buffers. Org
  already has `ox` for HTML/PDF, and `jsonyter-org-to-notebook`
  (`jsonyter.el:6470`) plus this command compose into a two-step path
  for anyone who wants it. Say so in the README rather than building a
  second export stack. (Org *script* export is in scope — §4.10.)

**Asynchrony.** `jsonyter--request-sync` blocks Emacs, and the bridge's
own default export deadline is **120 s** (`--export-timeout`,
`cli.py:506`) precisely because "a PDF render is seconds-to-minutes".
Blocking the editor for two minutes is not acceptable. Use
`jsonyter--send` with a `:result` callback, exactly as
`jsonyter--transfer-run` (`jsonyter.el:4184`) does for uploads. There
are no `progress` lines for export, so a simple "exporting…" message
plus a mode-line tag is enough — the `jsonyter--session-transfer` slot
(`jsonyter.el:441`) is the established pattern for a REST-pool operation
that wants to show itself in the mode line, and can be reused or
paralleled.

**Timeout plumbing.** `jsonyter--build-command` (`jsonyter.el:585`)
currently passes `--exec-timeout` but not `--export-timeout`. Add a
`jsonyter-export-timeout` defcustom (default 120, matching the bridge)
and pass it through; also accept a `timeout` param per request for a
one-off long render.

**Version gate.** The commentary header (`jsonyter.el:90`) declares
*"Requires jsonyter >= 0.2"*. Export needs **>= 2.0.0**. Bump the note,
and degrade gracefully against an older bridge: an unknown method comes
back as an error line, so catch it and say "this needs jsonyter >= 2.0;
upgrade with `pip install -U jsonyter`" rather than showing a raw
protocol error.

### 4.10 Script export — `jsonyter-notebook-export-script`

**Status: valid, and it must be built locally in `jsonyter.el`. nbconvert
cannot do it — verified, not assumed. Independent of §4.1–4.9: no
bridge, no server, no kernel.**

Extract the code cells from a notebook or Org file into a plain script
(`.py`, `.R`, `.jl`, `.sas`) with `# %%` dividers between cells, and
markdown cells wrapped as comment blocks.

**Direction is one-way — notebook/Org → script — and that is settled.**
The script is a deliverable for people who do not use notebooks; nothing
needs to import one back. Where reopening the result in
`jsonyter-script-mode` falls out for free it is kept (Python, R, Julia),
and where it does not it is dropped rather than engineered for
(**SAS — one-way, decided**). No requirement in this section is
justified by round-tripping.

#### 4.10.1 Why this does not go through nbconvert

nbconvert has `script` and `python` exporters, so the obvious move is to
route this through `export_notebook` like everything else in §4. **Don't
— neither produces what is being asked for.** Tested directly against
nbconvert 7.17.1 (`python3 -c "import nbconvert..."`, R and Python
fixture notebooks each with one markdown cell and two code cells):

`script` exporter, R notebook (and identically for Python):

```r
library('tibble')
q1dat <- 1


q1dat + 1

```

**The markdown cell is gone and there are no cell dividers at all** —
just code separated by blank lines. This is the only script exporter
that works for non-Python languages, and it discards exactly the two
things the feature is about.

`python` exporter (Python only):

```python
#!/usr/bin/env python
# coding: utf-8

# # Analysis
#
# Some **bold** prose.

# In[1]:


import numpy as np
```

Closer — markdown *is* preserved as `# ` comments — but the divider is
`# In[1]:`, not `# %%`, and it is Python-only. Worse, `# In[1]:` does
**not** match `jsonyter-script-cell-regexp` (verified: `NO MATCH`), so a
file exported this way does not open as cells in `jsonyter-script-mode`
— which is most of the point.

Full registered exporter list on that install: `asciidoc, custom, html,
latex, markdown, notebook, pdf, python, qtpdf, qtpng, rst, script,
slides, webpdf`. Nothing else is a candidate.

So this is a local text transformation. That is a **feature**, not a
consolation: script export then works with **no Jupyter server, no
kernel and no bridge at all** — the only part of §4 that does. It should
keep working offline, and should not be gated behind the
`list_export_formats` probe.

#### 4.10.2 Output format: follow Jupytext's percent format

Do not invent a format. Jupytext's "percent" format is the existing
standard for exactly this, and VS Code, Spyder and Jupytext itself all
read it:

```python
# %% [markdown]
# # Analysis
#
# Some **bold** prose and a [link](http://x).

# %%
import numpy as np

# %%
np.mean([1, 2, 3])
```

- code cell ⇒ `# %%` then the source verbatim;
- markdown cell ⇒ `# %% [markdown]` then every line prefixed with the
  comment character;
- raw cell ⇒ `# %% [raw]`, same commenting.

Verified against `jsonyter-script-cell-regexp`
(`jsonyter.el:4801`) — the cell-type suffix is accepted, because the
regexp only anchors through `%%`:

| Marker | Matches? |
| --- | --- |
| `# %%` | **MATCH** |
| `# %% [markdown]` | **MATCH** |
| `// %%`, `;; %%`, `% %%`, `#%%` | **MATCH** |
| `* %%;` (SAS comment) | **NO MATCH** |
| `/* %% */` (SAS block comment) | **NO MATCH** |
| `# In[1]:` (nbconvert's) | **NO MATCH** |

**Direction: this feature is one-way — notebook/Org → script — by
decision.** Nothing here needs to import a script back, and no
requirement should be derived from round-tripping. That said, for
Python, R and Julia the round trip **falls out for free**: the `# %%`
marker is already what `jsonyter-script-cell-regexp` matches, so an
exported script reopens in `jsonyter-script-mode` with exactly the cell
boundaries it was written with, at zero implementation cost. Keep that —
it is a free bonus, not a constraint. Do not spend effort *preserving*
it if it ever conflicts with producing a better script; the script is
the deliverable.

SAS does not get the round trip (trap 2 below) and that is accepted.

Where the round trip does work, a markdown cell becomes a script cell
containing only comments; running it sends comments to the kernel, which
is a harmless no-op. Worth a line in the docstring. Teaching
`jsonyter-script-run-cell` to skip a `[markdown]` cell is optional
polish and explicitly not required.

**The user's stated concession about markdown is the right call**, and
for a better reason than expedience: the whole point is that the script
goes to people who do not use notebooks, so the prose is there to be
*read*, not re-parsed. Wrapping it verbatim keeps it readable, keeps the
transformation lossless, is what Jupytext does, and avoids a pandoc
dependency (see §4.10.5). Do not try to strip or translate markdown
formatting.

#### 4.10.3 Comment syntax and file extension per language

There is **no language-to-extension map anywhere in `jsonyter.el`
today** — this has to be added. `jsonyter-script-languages`
(`jsonyter.el:4808`) maps major mode → language, which is the wrong
direction and does not carry extensions.

Proposed new defcustom, so users can extend it for languages jsonyter
does not ship:

| Language | Extension | Markdown commenting | Divider | Reopens as cells? |
| --- | --- | --- | --- | --- |
| python | `.py` | `# ` per line | `# %%` | yes |
| R | `.R` | `# ` per line | `# %%` | yes |
| julia | `.jl` | `# ` per line | `# %%` | yes |
| sas | `.sas` | `/* … */` around the cell | `* %%;` | **no — one-way** |

Note the SAS row differs in *kind*, not just in comment character — see
trap 2. Model this as a per-language function or a struct with a
block-comment slot, not as a single "comment prefix" string.

Two traps:

1. **`.R` vs `.r`.** The user asked for `.R`, which is the conventional
   R extension — but IRkernel declares `".r"` in the notebook's
   `language_info.file_extension`, and nbconvert duly emitted `.r` in
   the test above. So **prefer jsonyter's own map over
   `language_info.file_extension`**, falling back to the metadata only
   for a language the map does not know. The metadata is available:
   `jsonyter--nb-metadata` (`jsonyter.el:2490`) holds the whole
   top-level metadata plist. Note jsonyter's own new-notebook template
   (`jsonyter.el:3833`) writes `language_info` with only a `name` and no
   `file_extension`, so the fallback must tolerate its absence.

2. **SAS is one-way — decided, implement it that way.** SAS's comment
   forms are `* text;` and `/* text */`, and **neither matches
   `jsonyter-script-cell-regexp`** (verified above). There is no SAS
   comment syntax that is simultaneously valid SAS and a jsonyter cell
   marker.

   **Emit `* %%;` as the divider and document SAS export as one-way**:
   the result is valid, readable, runnable SAS, but does not reopen as
   cells in `jsonyter-script-mode`. Say so in the docstring and the
   README rather than leaving the user to discover it.

   Do **not** emit a bare `%%` line for SAS — `%` starts a macro
   reference there, so it is a syntax error rather than a comment.

   Extending `jsonyter-script-cell-regexp` with `\\*` so `* %%;` matches
   would buy the round trip back, and is genuinely a one-character
   change to a defcustom's default. It is **not** being done now, and
   should not be smuggled into this feature: it widens a user-facing
   defcustom that every script buffer reads, so it deserves its own
   change with its own tests. Record it as a possible follow-up.

   **The real SAS hazard is the markdown, not the divider.** A `* text;`
   comment *statement* is terminated by the **first semicolon**, so
   commenting markdown prose line-by-line with `*` is unsafe: any `;` in
   the user's prose ends the comment early and the rest of that line
   leaks into the script as SAS code. Prose containing a semicolon is
   entirely ordinary, so this would fire in practice.

   So for SAS, do not comment markdown per line. Wrap each markdown
   cell in a single `/* … */` block comment, which spans lines and is
   not semicolon-sensitive, and guard the one sequence that can close it
   early by replacing any `*/` inside the text (`* /` is the usual
   substitution). The divider stays `* %%;` — that text is jsonyter's
   own and contains no semicolon problem.

   This makes SAS the only language whose markdown commenting differs in
   kind rather than just in comment character, so the per-language table
   needs a block-comment column or a per-language function rather than a
   bare string. Worth designing for up front; retrofitting it after
   writing four `#`-prefix cases is the annoying path.

   SAS is the only affected language, and it is already the one jsonyter
   treats as a special case elsewhere (the language Org ships no babel
   backend for).

#### 4.10.4 Sources, and a pre-existing bug to route around

The renderer wants one input shape: a list of `(:cell_type ... :source
...)` plists — the same vocabulary `write_notebook` and
`export_notebook`'s `cells` take. Both surfaces can produce it, but only
one of them can today.

**Notebook buffer — straightforward.** `jsonyter--nb-collect-cells`
(`jsonyter.el:3057`) already yields exactly this shape. Script export
needs no outputs at all, so call it *without* the `include-outputs` flag
and none of §4.3's complications apply. This is the easy half.

**Org buffer — do not reuse `jsonyter--org-to-notebook-cells`.**
`jsonyter-org-to-notebook` (`jsonyter.el:6470`) looks like the obvious
building block, and its docstring promises *"ORG-FILE's cells: `jy:`
blocks and the prose between them"*. The implementation does not do
that. `jsonyter--org-notebook-cell-spans` (`jsonyter.el:6426`) splits
the buffer **only at `:JSONYTER_CELL_ID:` property drawers**
(`jsonyter--org-cell-id-re`, `jsonyter.el:6415`), and those are written
only by `jsonyter-org-from-notebook`. Fed a hand-authored Org file it
finds no drawers, treats the whole buffer as one span, and returns **a
single markdown cell containing the entire file verbatim** — source
blocks and all.

Verified both ways. Hand-written Org file (the user's homework shape):

```
cell_type="markdown" source="...the entire buffer, #+begin_src blocks included..."
```

The same notebook round-tripped through `jsonyter-org-from-notebook`
first, which writes the drawers:

```
cell_type="code"     source="x = 1"
cell_type="code"     source="print(x)"
cell_type="markdown" source="# heading"
```

So `jsonyter-org-to-notebook` silently produces a garbage notebook for
any Org file jsonyter did not itself generate. **That is a real
pre-existing bug** — the docstring describes the general behaviour, the
code implements the round-trip-only one — and it is worth its own fix,
but it should not block script export.

For script export, walk the Org buffer directly instead:
`jsonyter--org-goto-next-jy-block` (`jsonyter.el:5295`) for the code
cells, and the prose between consecutive blocks as the markdown cells,
skipping `#+KEYWORD:` lines the way
`jsonyter--org-notebook-span-empty-p` (`jsonyter.el:6419`) already does.

If you want to fix both at once, the shared fix is to have
`jsonyter--org-notebook-cell-spans` fall back to splitting at
`#+begin_src`/`#+end_src` boundaries when the buffer contains no id
drawers. That repairs `jsonyter-org-to-notebook` and gives script export
its input from one change — but it touches a working round-trip path, so
land it with tests of its own rather than folding it into this feature.

**`.ipynb` file on disk, not open in a buffer** — use the bridge's
`read_notebook` verb (local file, no server needed) and feed the result
to the same renderer. Cheap, and it makes the command usable from
`dired`.

#### 4.10.5 Do not route Org prose through the markdown converter

`jsonyter--org-notebook-cell-from-span` sends prose through
`jsonyter--org-markdown-convert` to turn Org into Markdown, which shells
out to pandoc. **Script export must not do this.** The prose is going
into comments verbatim either way, so converting it buys nothing and
costs a hard pandoc dependency.

This is not hypothetical: pandoc is absent in this container, and the
converter degrades by inserting a banner into the content itself —

```
[jsonyter: no Markdown->Org converter (install pandoc, or set
`jsonyter-org-markdown-converter') -- inserted verbatim]
```

— which would land in the exported script as if it were the user's own
prose. Take the Org text as-is and comment it.

#### 4.10.6 Proposed surface

```elisp
(defun jsonyter-notebook-export-script (file) ...)   ; notebook buffer
(defun jsonyter-org-export-script (file) ...)        ; org buffer
```

Plus a shared `jsonyter--cells-to-script (cells language)` doing the
actual rendering — one function, both callers, trivially testable
without a buffer, a bridge or a server.

- Interactively, default the filename to the buffer's own base name with
  the language's extension, via `read-file-name`.
- Refuse to clobber silently: `jsonyter-org-from-notebook` already
  signals `"jsonyter: %s already exists"` (confirmed in testing) — match
  that behaviour and that message shape.
- Synchronous is correct here. There is no server round trip, so none of
  §4.7's async machinery applies.
- Where §4.7's other commands must first check the
  `list_export_formats` probe, this one must **not** — it works with no
  server at all, and a probe failure must not block it.
- **Docstrings must state the direction and the SAS exception.** Say
  that export is one-way; that a Python/R/Julia result reopens in
  `jsonyter-script-mode`; and that a SAS result does not, and why. A
  user who exports SAS and then finds `C-c C-n` does nothing should find
  the answer in `C-h f`, not by reading this report.
- Same for the README's script section: one line that SAS is one-way.

#### 4.10.7 Tests

All of these run with no kernel, no bridge and no server — this is the
most testable part of §4, so there is no excuse for thin coverage.

1. **Output shape, per cell type.** Render a three-cell fixture
   (markdown, code, code) and assert the exact text: one divider per
   cell, the right marker for the cell type, code sources reproduced
   verbatim. This is the primary test — it pins the deliverable itself,
   independent of any round trip.
2. **Markdown commenting.** Every line of a markdown cell, blank lines
   included, comes out commented; no line escapes the comment prefix.
   Assert the result contains no uncommented prose — that is the failure
   that produces a syntax error in the user's script, and it is the
   whole risk of the "wrap it verbatim" approach.
3. **Per language.** Python, R and Julia produce `#`; the extension map
   gives `.py` / `.R` / `.jl`. Assert `.R` uppercase specifically (see
   §4.10.3's trap 1).
4. **SAS, one-way.** Two assertions, both of them the point of the
   decision:
   - markdown is wrapped in a single `/* … */`, **not** commented per
     line with `*`, and a markdown cell whose prose contains a semicolon
     still produces a fully commented block. This is trap 2's real
     hazard — test it with prose like `"Fit the model; then plot it."`,
     which is exactly the kind of sentence that breaks it.
   - a markdown cell containing `*/` does not close the comment early.
5. **Round trip, where it is free.** For Python/R/Julia only: splitting
   the rendered script on `jsonyter-script-cell-regexp` recovers the
   same number of cells with the same sources. Not a requirement — the
   feature is one-way — but it costs nothing today and this test is what
   stops someone silently losing it. Assert the complement for SAS:
   `* %%;` does **not** match, so the one-way claim in the docstring
   stays true and nobody "fixes" it by accident.
6. **Empty and edge cases.** A notebook with no code cells; a cell whose
   source has no trailing newline; a markdown cell containing a line
   that already looks like `# %%`. That last one is the one genuine
   correctness hazard in the feature — it must not produce a spurious
   divider — so test it deliberately even though nothing re-imports the
   file: a stray `# %%` mid-prose is confusing to a human reader too.
7. **Org, hand-written.** Assert a hand-authored Org file with two `jy:`
   blocks and prose between them yields three cells, not one. This is
   the §4.10.4 bug; the test should fail against
   `jsonyter--org-to-notebook-cells` and pass against whatever the
   script exporter uses, which documents why the reuse was rejected.

## 5. Org REPL: two distinct bugs

Both reported symptoms reproduce. They are **separate root causes**, and
the second one also re-triggers the first, which is why the feature feels
"clunky and often broken".

Test file used: the user's snippet verbatim (`#+PROPERTY: header-args:R
:session jy:stat525 :async yes`, two `#+begin_src R` blocks).

### 5a. Org run commands refuse to run unless `jsonyter-org-mode` is on

**Status: confirmed, exact error reproduced.**

```
jsonyter-org-mode=nil jsonyter-mode=nil
block-info lang="R"
session-key at point = ("R" . "stat525")
in-jy-block-p = t
RUN -> "jsonyter: not a jsonyter buffer — needs a REPL, a rendered .ipynb, or `jsonyter-script-mode'"
```

Note what this proves: the `#+PROPERTY:` line parses correctly, the
session key resolves to `("R" . "stat525")`, and
`jsonyter--org-in-jy-block-p` is `t`. **Everything jsonyter needs is
present.** The run is refused purely by a gate.

Chain: `jsonyter-org-run-block` → `jsonyter--org-connect`
(`jsonyter.el:5133`) → `jsonyter--ensure-live-bridge` →
`jsonyter--check-jsonyter-buffer` (`jsonyter.el:1926`), which requires
the buffer-local marker mode `jsonyter-mode`. `jsonyter-org-mode` sets
that in its enable body (`jsonyter.el:5698`); invoked by `M-x` in a plain
Org buffer, it was never set.

Three things are wrong here:

1. **The error message is actively misleading.** It names REPL, `.ipynb`
   and `jsonyter-script-mode` and never mentions `jsonyter-org-mode` —
   the one thing that would have fixed it. `jsonyter-mode`'s own
   docstring (`jsonyter.el:965`) has the same omission: it says "on in
   every jsonyter buffer" and then lists only three modes.
2. **The gate is doing nothing useful on the Org path.** `jsonyter-mode`
   is explicitly an inert marker with "no keymap or behavior of its own".
   The Org babel back door already knows this and works around it —
   `jsonyter--org-babel-ensure-plumbing` (`jsonyter.el:5757`) installs
   the buffer-locals and turns `jsonyter-mode` on itself, precisely so
   `C-c C-c` and export work with the minor mode off. The cell layer
   should do the same.
3. **The two front doors disagree**, which is the user-visible
   incoherence: on the identical buffer, `C-c C-c` works and `C-RET` /
   `S-RET` / `M-x jsonyter-org-run-block-and-advance` error out.

Also: the command the user typed, `jsonyter-org-run-cell-and-advance`,
does not exist — the real name is **`jsonyter-org-run-block-and-advance`**
(`jsonyter.el:5272`). Notebook and script say "cell", Org says "block".
Org's own vocabulary is "block", so the name is defensible, but a
`defalias` from `jsonyter-org-run-cell-and-advance` (and
`jsonyter-org-run-cell`) costs nothing and removes a guaranteed
papercut for anyone coming from the notebook surface.

**Suggested fix:** have the Org cell-layer entry points call
`jsonyter--org-babel-ensure-plumbing` (or a shared equivalent) the way
the babel path does, so running a `jy:` block from a plain Org buffer
just works. Failing that, at minimum make
`jsonyter--check-jsonyter-buffer` name `jsonyter-org-mode` in its error
when `(derived-mode-p 'org-mode)`, and point at
`jsonyter-org-mode-maybe`. Fixing the message alone is the weaker
option — the babel path already proves the gate is unnecessary here.

### 5b. Re-running `org-mode` silently destroys the session table and orphans the kernel

**Status: confirmed. This is the "new kernel for each cell" bug.**

```
SURVIVE: sessions before = 1
SURVIVE: after (org-mode): jsonyter-org-mode=nil sessions=0
SURVIVE: jsonyter--sessions is now nil
```

`jsonyter--sessions` and `jsonyter-org-mode` are buffer-local
(`jsonyter.el:443`). Any major-mode re-run calls
`kill-all-local-variables` and wipes both. The consequences:

- the running kernel is **orphaned** on the server — the `own` record
  that `jsonyter--cleanup` (`jsonyter.el:1883`) uses to shut it down at
  kill-buffer time is gone with the table, so it leaks until the server
  is restarted;
- the next block resolves the same key `("R" . "stat525")` against an
  **empty** table, so `jsonyter--connect-kernel` starts a **brand-new
  kernel** — with none of the previous blocks' state. Exactly the
  reported "cells which rely on previous cells fail";
- `jsonyter-org-mode` is now off, so the very next `C-RET` hits bug 5a
  again.

What makes this hit constantly rather than rarely: **`C-c C-c` on a
`#+PROPERTY:` line is the documented Org gesture for making that line
take effect, and it calls `org-mode-restart`, which re-runs `org-mode`**
(verified against the installed Org). `revert-buffer` and `normal-mode`
do the same. So the standard workflow for setting up the user's exact
file — add the `#+PROPERTY: header-args:R :session jy:stat525` line,
`C-c C-c` on it to activate it — destroys jsonyter's session state as a
side effect, every time.

Reassuringly, the design itself is sound. With the mode on and the table
intact, session reuse is correct:

```
MODE-ON key block1 = ("R" . "stat525")
MODE-ON key block2 = ("R" . "stat525")
MODE-ON same session object for both blocks = t
MODE-ON session count = 1
```

`jsonyter--connect-kernel` (`jsonyter.el:2300`) is explicitly idempotent
("a session that already has a live kernel is returned untouched"). One
kernel per `jy:` name is what the code does — right up until the table
is thrown away.

**Suggested fix**, in rough order of value:

1. **Survive a mode restart.** Either mark the session table with
   `put 'jsonyter--sessions 'permanent-local t` (same for
   `jsonyter--callbacks`, `jsonyter--process`, `jsonyter--session-key`),
   or re-establish from `change-major-mode-hook` /
   `after-change-major-mode-hook`. Permanent-local is the smaller change
   and is the idiomatic Emacs answer; verify the kill-buffer cleanup
   still fires, and that switching an Org buffer to a genuinely
   unrelated major mode does not strand the bridge process.
2. **Re-arm the minor mode.** Add `jsonyter-org-mode-maybe` to
   `org-mode-hook` from the package itself (or document loudly that the
   user must), so a restart turns the mode back on rather than leaving
   the buffer half-configured.
3. **Never silently start a second kernel.** If a `jy:` key has a
   `last-kernel` recorded but no live binding, reconnect to it (the
   `jsonyter-kernel-reconnect` path already exists) instead of starting
   a fresh one. Belt and braces for every other way the table can be
   lost.
4. **Surface it.** Once #2 lands, the kernel id in the mode line
   (report #2) makes this class of bug self-diagnosing — the id visibly
   changes the moment a new kernel is started. Worth doing #2 first for
   that reason.

### 5c. `:async yes` — a collision to check, not a confirmed bug

Not reproduced here and **not** the cause of the kernel-per-cell symptom
(5b is), but flag it for the implementer:

`jsonyter.el` defines its own `:async yes` handling for the babel path
(`jsonyter--org-babel-async-p`, `jsonyter.el:5834`). `ob-async` claims
the *same* header argument and implements it by running each block in a
**separate Emacs subprocess** via `async-start`. If the user has
`ob-async` loaded, its advice on `org-babel-execute-src-block` intercepts
before jsonyter's dispatch ever runs — and every block would then get a
fresh Emacs, a fresh session table, and its own kernel, producing
symptoms identical to 5b.

The agent should check whether `ob-async` is in play, and either detect
and warn about it, or document the incompatibility in the README's
"Async: `:async yes`" section (`README.md:778`), which currently does not
mention `ob-async` at all. Note also that `:async` has **no effect on the
`C-RET` cell layer** — that path is always async and ignores the header
entirely — so it does nothing useful in the user's `#+PROPERTY:` line as
written and could simply be dropped from it.

## Recommended order of work

**#4 (export) is the headline feature and the largest piece of work.**
It is no longer blocked — the bridge shipped it in 2.0.0 — and it is
worth its own branch. Everything else is small by comparison.

Suggested split across two workstreams, since they touch disjoint code:

**Stream A — export (§4).** Two independent halves:

- **A1: script export (§4.10).** Smaller, self-contained, needs no
  server or bridge, and the most testable thing in this report. Good
  first task, and it can run in parallel with A2.
- **A2: document export (§4.1–4.9).** Follow §4.9's internal order.
  Start with the `jsonyter--nb-collect-cells` outputs fix (§4.3); it is
  the one step that silently produces wrong output if skipped, and
  everything else is built on it.

A1 and A2 both touch `jsonyter--nb-collect-cells`, but A1 only *calls*
it (with no outputs) while A2 changes its signature — so land A2's
step 1 first if the same person is doing both, or accept a trivial
merge if not.

**Stream B — the bug fixes, in this order:**

1. **#1** — the notebook cursor bug, with the tests from §1. Self-contained, clear fix, clear regression test.
2. **#5b** — session table survival. Highest user impact of the bugs; silently leaks kernels.
3. **#5a** — let the Org cell layer bootstrap itself; fix the error message and the `jsonyter-mode` docstring; add the `run-cell` aliases.
4. **#2** — kernel id in the mode line. Makes #5b self-diagnosing.
5. **#3** — add `jsonyter-kernel-restart`, rename the misleading `jsonyter-reset`, docstring cross-references, README. Docs and aliases only.
6. **#5c** — `ob-async` check / README note.
7. **The `jsonyter-org-to-notebook` bug found in §4.10.4** — it silently
   produces a one-cell garbage notebook for any Org file jsonyter did
   not itself generate, because it splits only at `:JSONYTER_CELL_ID:`
   drawers while its docstring promises "blocks and the prose between
   them". Not part of any of the five reports; found while designing
   script export. Independent of everything above, and worth fixing on
   its own since the failure is silent.

Within stream B, items 1–5 are independent and can be done in any order;
none of them touch the same functions. The one ordering constraint
across streams: **#1 and §4.3 both touch the notebook cell layer** —
#1 edits `jsonyter--nb-show-output-as-text`, §4.3 edits
`jsonyter--nb-make-cell` and `jsonyter--nb-collect-cells`. Different
functions in the same region, so land one before starting the other to
avoid a needless conflict.
