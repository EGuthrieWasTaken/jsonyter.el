## 1. Run-and-advance leaves point at the start of the output block

**Status: confirmed. Notebook only — script and Org are not affected.**

### What happens

`jsonyter-notebook-run-cell-and-advance` (`jsonyter.el:3329`) advances
correctly, and then the arriving output drags point backwards.

Reproduced on the fixture notebook in `test/jsonyter-tests.el`, driving
the exact sequence `jsonyter-notebook-run-cell` performs:

```
after advance: point=7  cell1-start=7          ; correct
after output:  point=7  cell0-src-end=7  cell0-end=190  cell1-start=190
cell at point is cell 0 (the one just run!)
text after point: "output ───────────────────────"
```

Point does not move — the *buffer* moves out from under it. It ends up
at the first character of the just-run cell's output frame, with the
whole output between it and the next cell. Exactly as reported.

Both downstream symptoms confirmed:

```
REPEAT: cell-at-point is cell0? t
REPEAT: source jsonyter would re-send = "x = 1"     ; the SAME cell, silently, forever
REPEAT: typing here signals = "Text is read-only"
```

So pressing `S-RET` again re-executes the previous cell rather than
erroring — arguably worse than a failure, since nothing tells the user.
Typing gives `Text is read-only`.

### Root cause

`jsonyter--nb-show-output-as-text` (`jsonyter.el:2763`), the notebook
path that writes output as real buffer text.

In a rendered notebook, cells are laid down back to back: a cell's
overlay spans source *and* output, so `(overlay-end cell)` is exactly
`(overlay-start next-cell)`. On every output refresh the function does

```elisp
(save-excursion
  (delete-region src-end out-end)
  (goto-char src-end)
  ... (insert body) ...)
```

`save-excursion` saves point as a marker with insertion type `nil`,
sitting at `out-end`. `delete-region` collapses that marker to
`src-end`; the subsequent `insert` at `src-end` leaves an
insertion-type-`nil` marker *before* the inserted text. Point is
restored to the front of the new output.

The function already knows about this hazard — it explicitly fixes up
the adjacent cell overlays that suffer the identical collapse:

```elisp
(dolist (o adjacent) (move-overlay o (point) (overlay-end o)))
```

Point simply was not given the same treatment.

This only bites when the cell produces output (empty body ⇒ nothing
inserted ⇒ point is fine), and it fires on *every* refresh, so with
`jsonyter-stream-output` on it re-fires per chunk.

### Why script and Org are immune

Both are `jsonyter--overlay-string-cell-p` cells: their output is an
overlay `after-string` (`jsonyter--nb-show-output-as-string`,
`jsonyter.el:2744`), so no buffer text changes and no marker moves.
Verified for script mode:

```
SCRIPT: point before=21 after=21 (stable=t)
SCRIPT: line at point = "print(2)"
SCRIPT: output overlay end=16, point=21, point-after-output=t
```

`jsonyter-notebook-run-all` is also immune — it re-issues
`goto-char (overlay-start cell)` before each cell.

### Suggested fix

In `jsonyter--nb-show-output-as-text`, carry point across the rewrite
the way the adjacent overlays are carried. Either:

- record `(>= (point) out-end)` before the rewrite and `goto-char
  new-end` after it when that held; or
- replace the `save-excursion` with an explicit `(copy-marker out-end t)`
  (insertion type `t`, so it rides to the end of the inserted text) and
  `goto-char` it afterwards.

Prefer whichever reads better next to the existing `adjacent` fix-up,
and note in the comment that point and the adjacent overlays have the
same failure mode. Do **not** "fix" this in
`jsonyter-notebook-next-cell` (`jsonyter.el:3691`) — that function is
correct; the corruption happens afterwards, asynchronously, and would
still hit a user who advanced by hand.

Check the other `jsonyter--nb-refresh-output` callers still behave:
`jsonyter-notebook-clear-cell-output`, `jsonyter-notebook-clear-all-output`,
and the staleness path. Point ahead of the output region should stay put
in all of them; point *inside* the deleted region has nowhere valid to
go and landing at the new end is fine.

### Tests to add (explicitly requested)

There is currently **no test anywhere** — neither `test/jsonyter-tests.el`
nor `harness/profile/scenarios/` — asserting cursor position after any
`jsonyter-*-run-cell-and-advance`. The only adjacent assertion is
`harness/profile/scenarios/script.el:78`, which checks `C-c C-n` moves
forward. That gap is why this shipped.

Add to `test/jsonyter-tests.el`, using the existing
`jsonyter-tests--with-notebook` / `jsonyter-tests--cell` /
`jsonyter-tests--stream` helpers (no kernel needed — feed output in
kernel shape, as the file's other tests do):

1. **Notebook, the regression.** Go to cell 0; `jsonyter--nb-set-output`
   to `""` (what run-cell does pre-send); `jsonyter-notebook-next-cell`;
   then `jsonyter--nb-append-output` a multi-line stream. Assert
   `(= (point) (overlay-start (jsonyter-tests--cell 1)))` and
   `(eq (jsonyter--nb-cell-at) (jsonyter-tests--cell 1))`.
   Both fail before the fix.
2. **Notebook, streaming.** Same, with several `append-output` calls, so
   the per-chunk refresh path is covered too.
3. **Notebook, idempotence.** After the above, assert
   `(jsonyter--nb-cell-source (jsonyter--nb-cell-at))` is cell 1's
   source, not cell 0's — i.e. a second `S-RET` would run the *next*
   cell. This is the assertion that pins the user-visible bug.
4. **Notebook, last cell.** Advancing off the final cell must not error
   and must not land in output.
5. **Script and Org, guard rails.** Assert point is unchanged when
   output arrives after `jsonyter-script-next-cell` /
   `jsonyter-org-next-block`. These pass today; add them so the
   eventual fix does not regress the overlay-string surfaces.

## 2. Kernel id in the mode line

**Status: valid, small, nothing blocking it.**

`jsonyter--session-status-tag` (`jsonyter.el:1129`) renders state only —
`:idle`, `:run`, `:run[ext]`, `:dead`, `:restarting`, `:offline`,
`:starting`, `:no-kernel`, and transfer progress. No id anywhere.

Everything needed already exists:

- `jsonyter--short-id` (`jsonyter.el:1920`) — first 8 chars, already used
  in the REPL banner, already handles a nil/short id.
- `jsonyter-current-kernel-id` (`jsonyter.el:517`) — public accessor.
- `jsonyter--mode-line-string` (`jsonyter.el:1152`) already resolves the
  Org session **at point**, so this automatically satisfies the Org half
  of report #5 ("put it in the bottom bar") with no extra work.

### Notes for the implementer

- Put it in `jsonyter--session-status-tag`, not
  `jsonyter--mode-line-string`, so all four surfaces get it from one
  place.
- Suggested shape `:idle[3f8a9c21]` or `:3f8a9c21/idle` — pick one and
  apply it consistently. Keep it short; this is `mode-line-process` and
  competes for space.
- Make it a defcustom (e.g. `jsonyter-mode-line-show-kernel-id`,
  default `t`). Users on narrow frames will want it off.
- Leave the multi-session summary branch (`:2 kernels!`) alone — ids
  there would be unreadable.
- Show nothing rather than `?` when there is no kernel; `:no-kernel`
  already says it.
- Tests: `jsonyter--session-status-tag` is a pure function of a session
  struct, so assert its output directly for a bound session, an unbound
  one, and with the defcustom off.

## 3. `jsonyter-kernel-reset`

**Status: already implemented, under a different name. Do not add a new command — fix the naming and the docs.**

`jsonyter-restart` (`jsonyter.el:1775`) is exactly the request:

- docstring: *"Restart SESSION's kernel (default the session in play), **keeping its id**"*
- calls the bridge's `restart_kernel` with `:kernel_id id` and keeps
  using that same `id` afterwards — the id is preserved by construction
  (this is Jupyter's `POST /api/kernels/{id}/restart` semantics)
- prompts *"Restart the kernel (all state will be lost)?"* — the kernel
  process is replaced, so all state is cleared
- also drops the stale websocket, renews the event subscription, clears
  the busy flag, and blanks notebook execution counts via
  `jsonyter--after-kernel-reset`
- bound to `C-c C-r` on every surface, plus `jsonyter-org-restart`
  (`jsonyter.el:5325`) for the session at point

### The actual problem

The command *named* `jsonyter-reset` (`jsonyter.el:1818`) does something
completely different: it clears the **client's** busy flag to unstick a
REPL, and deliberately **leaves the kernel running** — its own docstring
says *"[reset — kernel left running]"*. It is bound to `C-c C-k`.

So a user looking for "reset the kernel" finds `jsonyter-reset`, gets a
command that does not touch the kernel, and concludes the feature is
missing. That is a genuine discoverability bug and matches this report
precisely.

### Suggested change

1. Add `jsonyter-kernel-restart` as an alias for `jsonyter-restart`
   (`defalias`), so the `jsonyter-kernel-*` family — `jsonyter-kernel-connect`,
   `jsonyter-kernel-reconnect`, `jsonyter-kernel-history` — is where a
   user looking for kernel operations actually finds it. An alias, not a
   rename: `jsonyter-restart` is in the README, the commentary header
   and the key tables.
2. Rename the misleading one to `jsonyter-unstick` (or
   `jsonyter-repl-unstick`), keeping `jsonyter-reset` as an obsolete
   alias via `define-obsolete-function-alias`.
3. Cross-reference them in both docstrings: `jsonyter-reset` should say
   "to restart the kernel itself and discard its state, use
   `jsonyter-restart'"; `jsonyter-restart` should say "to merely unstick
   a REPL without touching the kernel, see `jsonyter-reset'".
4. README: the REPL key table lists both `C-c C-r` and `C-c C-k` without
   making the distinction obvious. Spell out that one replaces the kernel
   process (same id, no state) and the other touches only Emacs.

If after this the user still wants a distinct `jsonyter-kernel-reset`,
the only behaviour not already covered would be restart **plus** clearing
displayed output (`jsonyter-clear`) in one gesture. Worth asking before
building it.

## 4. Export via the Jupyter API (`jsonyter-notebook-export-*`)

**Status: no, it does not exist, and it is not hiding under a different name.**

The bridge protocol is a closed set of named verbs. The complete list
used by `jsonyter.el`:

```
start_kernel  get_kernel  list_kernels  list_kernelspecs
restart_kernel  shutdown_kernel  interrupt_kernel  disconnect
subscribe  execute  complete  inspect  history
list_contents  read_notebook  write_notebook  upload  download
```

No `nbconvert`, no `export`, no generic HTTP passthrough that could be
pointed at one — file transfer goes through dedicated `upload` /
`download` verbs (`jsonyter--transfer-run`, `jsonyter.el:4184`), not a
general REST call. Searching for `nbconvert` in `jsonyter.el` hits only
prose comments about how MathJax reads LaTeX macros.

The nearest existing things, neither of which is export:

- `jsonyter-notebook-save-with-outputs` — writes `.ipynb` via `write_notebook`
- the Org↔notebook converters (`jsonyter.el:6287`, `6362`)
- `org-babel-tangle` integration, which emits `# %%` scripts

### What building it would take

This is **not a `jsonyter.el`-only change**. Jupyter Server does ship
nbconvert handlers (`GET /nbconvert/<format>/<path>`, formats drawn from
nbconvert's registered exporters), but reaching them requires a new verb
in the **`jsonyter` Python bridge** (separate repo,
`EGuthrieWasTaken/jsonyter`) before any Emacs-side command can exist. An
agent picking this up should:

1. Confirm against the deployed server whether the nbconvert handlers
   are actually enabled — they are commonly disabled, and WebPDF in
   particular needs Playwright installed server-side, so it will often be
   unavailable even when HTML works.
2. Add a bridge verb (e.g. `export_notebook` taking `path` + `format`,
   returning bytes or a server path) and bump the bridge version floor
   in the `jsonyter.el` commentary header (currently `>= 0.2`).
3. Only then add the Emacs commands. The proposed naming is good and
   matches house style: `jsonyter-notebook-export-html`,
   `-pdf`, `-webpdf`, `-markdown`, `-latex`, plus a
   `jsonyter-notebook-export` that completes over the formats the server
   actually reports rather than a hardcoded list.
4. Degrade honestly: a clear `user-error` naming the missing exporter,
   not a silent failure — same posture as the existing
   "older bridge" handling.

Recommend answering the user's question first and scoping the bridge
work separately; it should not be bundled with the bug fixes above.

## 5. Org REPL: two distinct bugs

Both reported symptoms reproduce. They are **separate root causes**, and
the second one also re-triggers the first, which is why the feature feels
"clunky and often broken".

Test file used: the user's snippet verbatim (`#+PROPERTY: header-args:R
:session jy:stat525 :async yes`, two `#+begin_src R` blocks).

### 5a. Org run commands refuse to run unless `jsonyter-org-mode` is on

**Status: confirmed, exact error reproduced.**

```
jsonyter-org-mode=nil jsonyter-mode=nil
block-info lang="R"
session-key at point = ("R" . "stat525")
in-jy-block-p = t
RUN -> "jsonyter: not a jsonyter buffer — needs a REPL, a rendered .ipynb, or `jsonyter-script-mode'"
```

Note what this proves: the `#+PROPERTY:` line parses correctly, the
session key resolves to `("R" . "stat525")`, and
`jsonyter--org-in-jy-block-p` is `t`. **Everything jsonyter needs is
present.** The run is refused purely by a gate.

Chain: `jsonyter-org-run-block` → `jsonyter--org-connect`
(`jsonyter.el:5133`) → `jsonyter--ensure-live-bridge` →
`jsonyter--check-jsonyter-buffer` (`jsonyter.el:1926`), which requires
the buffer-local marker mode `jsonyter-mode`. `jsonyter-org-mode` sets
that in its enable body (`jsonyter.el:5698`); invoked by `M-x` in a plain
Org buffer, it was never set.

Three things are wrong here:

1. **The error message is actively misleading.** It names REPL, `.ipynb`
   and `jsonyter-script-mode` and never mentions `jsonyter-org-mode` —
   the one thing that would have fixed it. `jsonyter-mode`'s own
   docstring (`jsonyter.el:965`) has the same omission: it says "on in
   every jsonyter buffer" and then lists only three modes.
2. **The gate is doing nothing useful on the Org path.** `jsonyter-mode`
   is explicitly an inert marker with "no keymap or behavior of its own".
   The Org babel back door already knows this and works around it —
   `jsonyter--org-babel-ensure-plumbing` (`jsonyter.el:5757`) installs
   the buffer-locals and turns `jsonyter-mode` on itself, precisely so
   `C-c C-c` and export work with the minor mode off. The cell layer
   should do the same.
3. **The two front doors disagree**, which is the user-visible
   incoherence: on the identical buffer, `C-c C-c` works and `C-RET` /
   `S-RET` / `M-x jsonyter-org-run-block-and-advance` error out.

Also: the command the user typed, `jsonyter-org-run-cell-and-advance`,
does not exist — the real name is **`jsonyter-org-run-block-and-advance`**
(`jsonyter.el:5272`). Notebook and script say "cell", Org says "block".
Org's own vocabulary is "block", so the name is defensible, but a
`defalias` from `jsonyter-org-run-cell-and-advance` (and
`jsonyter-org-run-cell`) costs nothing and removes a guaranteed
papercut for anyone coming from the notebook surface.

**Suggested fix:** have the Org cell-layer entry points call
`jsonyter--org-babel-ensure-plumbing` (or a shared equivalent) the way
the babel path does, so running a `jy:` block from a plain Org buffer
just works. Failing that, at minimum make
`jsonyter--check-jsonyter-buffer` name `jsonyter-org-mode` in its error
when `(derived-mode-p 'org-mode)`, and point at
`jsonyter-org-mode-maybe`. Fixing the message alone is the weaker
option — the babel path already proves the gate is unnecessary here.

### 5b. Re-running `org-mode` silently destroys the session table and orphans the kernel

**Status: confirmed. This is the "new kernel for each cell" bug.**

```
SURVIVE: sessions before = 1
SURVIVE: after (org-mode): jsonyter-org-mode=nil sessions=0
SURVIVE: jsonyter--sessions is now nil
```

`jsonyter--sessions` and `jsonyter-org-mode` are buffer-local
(`jsonyter.el:443`). Any major-mode re-run calls
`kill-all-local-variables` and wipes both. The consequences:

- the running kernel is **orphaned** on the server — the `own` record
  that `jsonyter--cleanup` (`jsonyter.el:1883`) uses to shut it down at
  kill-buffer time is gone with the table, so it leaks until the server
  is restarted;
- the next block resolves the same key `("R" . "stat525")` against an
  **empty** table, so `jsonyter--connect-kernel` starts a **brand-new
  kernel** — with none of the previous blocks' state. Exactly the
  reported "cells which rely on previous cells fail";
- `jsonyter-org-mode` is now off, so the very next `C-RET` hits bug 5a
  again.

What makes this hit constantly rather than rarely: **`C-c C-c` on a
`#+PROPERTY:` line is the documented Org gesture for making that line
take effect, and it calls `org-mode-restart`, which re-runs `org-mode`**
(verified against the installed Org). `revert-buffer` and `normal-mode`
do the same. So the standard workflow for setting up the user's exact
file — add the `#+PROPERTY: header-args:R :session jy:stat525` line,
`C-c C-c` on it to activate it — destroys jsonyter's session state as a
side effect, every time.

Reassuringly, the design itself is sound. With the mode on and the table
intact, session reuse is correct:

```
MODE-ON key block1 = ("R" . "stat525")
MODE-ON key block2 = ("R" . "stat525")
MODE-ON same session object for both blocks = t
MODE-ON session count = 1
```

`jsonyter--connect-kernel` (`jsonyter.el:2300`) is explicitly idempotent
("a session that already has a live kernel is returned untouched"). One
kernel per `jy:` name is what the code does — right up until the table
is thrown away.

**Suggested fix**, in rough order of value:

1. **Survive a mode restart.** Either mark the session table with
   `put 'jsonyter--sessions 'permanent-local t` (same for
   `jsonyter--callbacks`, `jsonyter--process`, `jsonyter--session-key`),
   or re-establish from `change-major-mode-hook` /
   `after-change-major-mode-hook`. Permanent-local is the smaller change
   and is the idiomatic Emacs answer; verify the kill-buffer cleanup
   still fires, and that switching an Org buffer to a genuinely
   unrelated major mode does not strand the bridge process.
2. **Re-arm the minor mode.** Add `jsonyter-org-mode-maybe` to
   `org-mode-hook` from the package itself (or document loudly that the
   user must), so a restart turns the mode back on rather than leaving
   the buffer half-configured.
3. **Never silently start a second kernel.** If a `jy:` key has a
   `last-kernel` recorded but no live binding, reconnect to it (the
   `jsonyter-kernel-reconnect` path already exists) instead of starting
   a fresh one. Belt and braces for every other way the table can be
   lost.
4. **Surface it.** Once #2 lands, the kernel id in the mode line
   (report #2) makes this class of bug self-diagnosing — the id visibly
   changes the moment a new kernel is started. Worth doing #2 first for
   that reason.

### 5c. `:async yes` — a collision to check, not a confirmed bug

Not reproduced here and **not** the cause of the kernel-per-cell symptom
(5b is), but flag it for the implementer:

`jsonyter.el` defines its own `:async yes` handling for the babel path
(`jsonyter--org-babel-async-p`, `jsonyter.el:5834`). `ob-async` claims
the *same* header argument and implements it by running each block in a
**separate Emacs subprocess** via `async-start`. If the user has
`ob-async` loaded, its advice on `org-babel-execute-src-block` intercepts
before jsonyter's dispatch ever runs — and every block would then get a
fresh Emacs, a fresh session table, and its own kernel, producing
symptoms identical to 5b.

The agent should check whether `ob-async` is in play, and either detect
and warn about it, or document the incompatibility in the README's
"Async: `:async yes`" section (`README.md:778`), which currently does not
mention `ob-async` at all. Note also that `:async` has **no effect on the
`C-RET` cell layer** — that path is always async and ignores the header
entirely — so it does nothing useful in the user's `#+PROPERTY:` line as
written and could simply be dropped from it.

## Recommended order of work

1. **#1** — the notebook cursor bug, with the tests from §1. Self-contained, clear fix, clear regression test.
2. **#5b** — session table survival. Highest user impact; silently leaks kernels.
3. **#5a** — let the Org cell layer bootstrap itself; fix the error message and the `jsonyter-mode` docstring; add the `run-cell` aliases.
4. **#2** — kernel id in the mode line. Makes #5b self-diagnosing.
5. **#3** — aliases, renames, docstring cross-references, README. Docs only.
6. **#5c** — `ob-async` check / README note.
7. **#4** — export. Blocked on bridge work in another repo; scope separately.

Items 1–5 are independent and can be done in any order within the group;
none of them touch the same functions.
